# Паралельне сортування підрахунком

Практична робота 2, варіант 3. Основна реалізація — Python. Додаткове порівняння: **C++, Rust, Go та Node.js**. Усі версії рахують частоти у приватних копіях блоків, після чого головний працівник послідовно додає гістограми та формує відсортований результат.

## Код

| Файл | Реалізація |
| --- | --- |
| [`counting_sort.py`](counting_sort.py) | Послідовна версія і пул процесів Python (`spawn`) |
| [`multilang/count_cpp.cpp`](multilang/count_cpp.cpp) | C++17, пул `std::thread` |
| [`multilang/count_rust.rs`](multilang/count_rust.rs) | Rust, стандартні потоки і канали |
| [`multilang/count_go.go`](multilang/count_go.go) | Go, горутини і канали |
| [`multilang/count_node.mjs`](multilang/count_node.mjs) | Node.js, `worker_threads`, передавання власності на буфери |
| [`multilang/experiment.py`](multilang/experiment.py) | Збірка, перевірки, спільні входи та вимірювання |
| [`multilang/plots.py`](multilang/plots.py) | Графіки з CSV |

**OpenMP у цих реалізаціях не використовується.** Процеси Python обмінюються серіалізованими копіями. Потоки C++/Rust, горутини Go та workers Node.js мають приватні блоки й гістограми. Node.js використовує transferable `ArrayBuffer`, без `SharedArrayBuffer`; потоки все одно працюють в одному адресному просторі.

## Запуск

Для основної Python-версії достатньо стандартної бібліотеки Python 3.10+:

```bash
git clone https://github.com/blcktqq/parallel-counting-sort-benchmark.git
cd parallel-counting-sort-benchmark
python3 counting_sort.py
python3 counting_sort.py --self-test
```

Для порівняння потрібні `g++` із підтримкою C++17, `rustc` із підтримкою edition 2021, `go` та Node.js. Перевірено з Python 3.12, GCC 13.3, Rust 1.85, Go 1.24 і Node.js 24.19 на Linux. Скрипт не встановлює залежностей і не потребує мережі. Якщо компілятори встановлено поза PATH, задай `CXX`, `RUSTC`, `GO`, `NODE` як шлях до відповідної програми.

Швидка перевірка всіх п’яти реалізацій із невеликими входами:

```bash
python3 multilang/experiment.py --quick
```

Повне порівняння (потрібно кілька хвилин і запас оперативної пам’яті; виміряно на машині з 8 GiB):

```bash
python3 multilang/experiment.py
```

Результати нового запуску: `multilang/results/`; швидкого: `multilang/smoke-results/`. Вхідні бінарні файли генеруються в `multilang/data/`, виконувані файли — у `multilang/bin/`. Ці каталоги виключено з Git.

Для графіків встанови додаткові Python-пакети в окреме середовище:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python multilang/plots.py
# Або відтворити графіки з опублікованих вимірювань:
python multilang/plots.py results/reference
```

Окремий початковий експеримент лише на Python:

```bash
python3 counting_sort.py --benchmark --output results/local-python
```

## Методика

- Спільні входи: little-endian `int32`, рівномірні ключі, seed 42; SHA-256 кожного файла збережено у `inputs.json`.
- Повний набір: `n = 10 000, 100 000, 1 000 000, 10 000 000`; `K = 256, 65 536`; `p = 1, 2, 4`; 5 повторів.
- **Seq** — послідовне сортування. **Warm** — готовий пул. **Cold** — також створення та завершення працівників; запуск головного процесу програми сюди не входить. Горутини Go можуть повторно використовувати потоки ОС.
- Таймер включає виділення пам’яті, копії блоків, передавання задач, гістограми, їх додавання та відновлення виходу. Генерація/читання входу, компіляція, еталонне сортування й перевірка рівності — поза таймером.
- У Node.js перед вимірюванням виконуються 10 прогрівів seq/warm; cold має один попередній запуск із новими workers. У решті реалізацій — один прогрів на конфігурацію. Це враховує JIT, але не гарантує однакового стану оптимізатора кожного нового worker.
- Go та Node.js використовують стандартний GC. Збирання сміття, яке потрапило в інтервал, враховане; звільнення тимчасових об’єктів може відбуватися в різний момент. У C++/Rust звільнення визначається областю видимості.
- Кожен виміряний вихід цілком порівнюється з еталонним сортуванням. Python додатково перевіряє 80 наборів і 6 некоректних входів; C++/Rust/Go — 60 наборів у трьох режимах; Node.js — 60 наборів у seq/warm і 3 cold-випадки.
- Швидка перевірка дає 420 часових зразків, повний запуск — 1400. Прискорення `S = T_seq / T_p` обчислюється відносно послідовної версії тієї самої мови; ефективність `E = S / p`.

Це порівняння конкретних програм і моделей виконання. Python працює з об’єктами `int` та IPC; інші версії — з компактними ключами int32. Гістограми C++/Rust/Go мають 64-бітні цілі лічильники; Node.js — `Float64Array`, який точно представляє всі цілі частоти в перевіреному діапазоні (до 10 млн).

## Результати та звіт

[`docs/practical-2-report.pdf`](docs/practical-2-report.pdf) містить пояснення, формули, блок-схему та результати. [`results/reference/`](results/reference/) містить повний прогін п’яти мов: сирі CSV, медіани, мінімум/максимум, середовище, контрольні суми входів і графіки. [`results/python-original/`](results/python-original/) — окремий початковий експеримент Python зі змінним діапазоном і сталими даними.

Час залежить від машини, квот CPU, представлення даних, алокацій, диспетчеризації та GC. П’ять повторів в одній сесії не доводять загальної переваги мови. Якщо Go випереджає C++/Rust, це встановлює перевагу цих реалізацій на конкретних входах. Точну причину без окремого профілювання фаз не встановлено; пояснення через алокації, звільнення пам’яті чи GC є гіпотезами.
