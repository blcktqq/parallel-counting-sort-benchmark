# Паралельне сортування підрахунком

Практична робота 2, варіант 3. Основна реалізація — Python; додано скомпільований модуль **Cython + OpenMP** без написання C++. Базове порівняння: **C++, Rust, Go та Node.js**. Усі версії рахують частоти у приватних копіях блоків, після чого головний працівник послідовно додає гістограми та формує відсортований результат.

## Код

| Файл | Реалізація |
| --- | --- |
| [`openmp/omp_counting.py`](openmp/omp_counting.py) | Cython у Python-синтаксисі, OpenMP `prange`, компіляція в C |
| [`counting_sort.py`](counting_sort.py) | Послідовна версія і пул процесів Python (`spawn`) |
| [`multilang/count_cpp.cpp`](multilang/count_cpp.cpp) | C++17, пул `std::thread` |
| [`multilang/count_rust.rs`](multilang/count_rust.rs) | Rust, стандартні потоки і канали |

| [`multilang/count_node.mjs`](multilang/count_node.mjs) | Node.js, `worker_threads`, передавання власності на буфери |
| [`multilang/experiment.py`](multilang/experiment.py) | Збірка, перевірки, спільні входи та вимірювання |
| [`multilang/plots.py`](multilang/plots.py) | Графіки з CSV |

**У базовому порівнянні п’яти мов OpenMP не використовується; окремий модуль Cython використовує OpenMP.** Процеси Python мають окремі адресні простори й обмінюються серіалізованими копіями. **Горутини Go, потоки C++/Rust і OpenMP працюють у спільному адресному просторі.** Копія блоку та приватна гістограма усувають спільні записи лічильників, але не створюють ізоляції пам’яті. У Go канали передають slice-дескриптори без серіалізації буферів. Node.js використовує окремі JS-ізоляти й transferable `ArrayBuffer`, без `SharedArrayBuffer`; після передавання відправник втрачає доступ до буфера.

## Запуск

Для основної Python-версії достатньо стандартної бібліотеки Python 3.10+:

```bash
git clone https://github.com/blcktqq/parallel-counting-sort-benchmark.git
cd parallel-counting-sort-benchmark
python3 counting_sort.py
python3 counting_sort.py --self-test
```

Для порівняння потрібні `g++` із підтримкою C++17, `rustc` із підтримкою edition 2021, `go` та Node.js. Перевірено з Python 3.12, GCC 13.3, Rust 1.85, Go 1.24 і Node.js 24.19 на Linux. Скрипт не встановлює залежностей і не потребує мережі. Якщо компілятори встановлено поза PATH, задай `CXX`, `RUSTC`, `GO`, `NODE` як шлях до відповідної програми.

Швидка перевірка всіх п’яти реалізацій із невеликими входами:

```bash
python3 multilang/experiment.py --quick
```

Повне порівняння (потрібно кілька хвилин і запас оперативної пам’яті; виміряно на машині з 8 GiB):

```bash
python3 multilang/experiment.py
```

Результати нового запуску: `multilang/results/`; швидкого: `multilang/smoke-results/`. Вхідні бінарні файли генеруються в `multilang/data/`, виконувані файли — у `multilang/bin/`. Ці каталоги виключено з Git.

Для графіків встанови додаткові Python-пакети в окреме середовище:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python multilang/plots.py
# Або відтворити графіки з опублікованих вимірювань:
python multilang/plots.py results/reference
```

Окремий початковий експеримент лише на Python:

```bash
python3 counting_sort.py --benchmark --output results/local-python
```

## Cython + OpenMP без C++

Це **Python-синтаксис із типами Cython**, скомпільований у C, а потім у модуль Python. Для збірки потрібні GCC з OpenMP та заголовки Python. Перевірено на Linux, GCC 13.3 і Cython 3.3.0; Windows/macOS потребують окремих налаштувань компілятора OpenMP.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-openmp.txt
python openmp/setup.py build_ext --inplace
python openmp/experiment.py --self-test
python openmp/experiment.py
```

Приклад із Python після збірки:

```python
from array import array
import omp_counting

out, actual_threads = omp_counting.sort(
    array("i", [4, -1, 2, 4, 0, -1, 3, 2]), lo=-1, k=6, workers=4
)
print(out.tolist())  # [-1, -1, 0, 2, 2, 3, 4, 4]
print(actual_threads)
```

`workers=0` запускає послідовну базу; `1, 2, 4` — OpenMP. `prange(..., nogil=True, num_threads=p)` розподіляє p блоків між потоками. Перед циклом вхід копіюється в буфер із неперетинними діапазонами; кожен блок записує тільки власний рядок гістограми. Неявний бар’єр після `prange` гарантує завершення підрахунків перед послідовним об’єднанням. Спільний адресний простір тут використовується навмисно.

Вхід і вихід — компактні int32 (`array('i')`), лічильники — uint64. Не змінюй вхід одночасно з викликом; запускати функцію слід із головного потоку. Звичайні списки можна перетворити на `array('i')` до виклику; у вимірюваннях це перетворення поза таймером, як читання типізованого входу в інших скомпільованих версіях.

Для спільного запуску всіх реалізацій після встановлення компіляторів і збірки модуля:

```bash
python run_experiments.py --quick --with-openmp
python run_experiments.py --with-openmp
```

OpenMP має окремі `seq` і `parallel` результати: кожен виклик відкриває паралельну область, а середовище OpenMP може зберігати потоки ОС. Його не позначено `cold`, оскільки це не еквівалент створення й завершення наших пулів. Повний OpenMP-прогін: ті самі 8 входів, p = 1, 2, 4, 5 повторів і 160 вимірювань. Час включає алокації, копіювання в паралельному варіанті, підрахунок, об’єднання, запис виходу та звільнення локальних буферів. Перевірка виходу поза таймером. Фактичні розміри команд записано в CSV; квоти або `OMP_THREAD_LIMIT` можуть обмежити кількість потоків.

Опубліковані OpenMP-результати: [`results/openmp-reference/`](results/openmp-reference/). Вони отримані окремою серією після базових п’яти мов на тій самій машині. SHA-256 входів звірено, але міжсерійні абсолютні часи слід порівнювати з урахуванням розкиду. Новий запуск записує файли в `openmp/results/`. Графік можна відтворити командою `python openmp/plots.py results/openmp-reference` після встановлення `requirements.txt`.

## Методика базового порівняння

- Спільні входи: little-endian `int32`, рівномірні ключі, seed 42; SHA-256 кожного файла збережено у `inputs.json`.
- Повний набір: `n = 10 000, 100 000, 1 000 000, 10 000 000`; `K = 256, 65 536`; `p = 1, 2, 4`; 5 повторів.
- **Seq** — послідовне сортування. **Warm** — готовий пул. **Cold** — також створення та завершення працівників; запуск головного процесу програми сюди не входить. Горутини Go можуть повторно використовувати потоки ОС.
- Таймер включає виділення пам’яті, копії блоків, передавання задач, гістограми, їх додавання та відновлення виходу. Генерація/читання входу, компіляція, еталонне сортування й перевірка рівності — поза таймером.
- У Node.js перед вимірюванням виконуються 10 прогрівів seq/warm; cold має один попередній запуск із новими workers. У решті реалізацій — один прогрів на конфігурацію. Це враховує JIT, але не гарантує однакового стану оптимізатора кожного нового worker.
- Go та Node.js використовують стандартний GC. Збирання сміття, яке потрапило в інтервал, враховане; звільнення тимчасових об’єктів може відбуватися в різний момент. У C++/Rust звільнення визначається областю видимості.
- Кожен виміряний вихід цілком порівнюється з еталонним сортуванням. Python додатково перевіряє 80 наборів і 6 некоректних входів; C++/Rust/Go — 60 наборів у трьох режимах; Node.js — 60 наборів у seq/warm і 3 cold-випадки.
- Швидка перевірка дає 420 часових зразків, повний запуск — 1400. Прискорення `S = T_seq / T_p` обчислюється відносно послідовної версії тієї самої мови; ефективність `E = S / p`.

Це порівняння конкретних програм і моделей виконання. Python працює з об’єктами `int` та IPC; інші версії — з компактними ключами int32. Гістограми C++/Rust/Go мають 64-бітні цілі лічильники; Node.js — `Float64Array`, який точно представляє всі цілі частоти в перевіреному діапазоні (до 10 млн).

## Результати та звіт

[`docs/practical-2-report.pdf`](docs/practical-2-report.pdf) містить пояснення, формули, блок-схему та результати. [`results/reference/`](results/reference/) містить повний прогін п’яти мов: сирі CSV, медіани, мінімум/максимум, середовище, контрольні суми входів і графіки. [`results/python-original/`](results/python-original/) — окремий початковий експеримент Python зі змінним діапазоном і сталими даними.

Час залежить від машини, квот CPU, представлення даних, алокацій, диспетчеризації та GC. П’ять повторів в одній сесії не доводять загальної переваги мови. Якщо Go випереджає C++/Rust, це встановлює перевагу цих реалізацій на конкретних входах. Точну причину без окремого профілювання фаз не встановлено; пояснення через алокації, звільнення пам’яті чи GC є гіпотезами.

### Приклад: 10 млн елементів, K = 256

Медіана п’яти повторів, мілісекунди; це результати опублікованого прогону.

| Мова | Seq, мс | Warm p=4, мс | Cold p=4, мс | Прискорення warm |
| --- | ---: | ---: | ---: | ---: |
| Python | 850.072 | 773.255 | 959.263 | 1.10 |
| C++ | 22.313 | 23.326 | 24.864 | 0.96 |
| Rust | 18.539 | 22.018 | 19.097 | 0.84 |
| Go | 17.008 | 15.825 | 17.759 | 1.07 |
| Node.js | 44.427 | 32.983 | 99.290 | 1.35 |

### Cython + OpenMP: 10 млн елементів

Окрема серія вимірювань; медіана п’яти повторів, мс.

| K | Seq | p=1 | p=2 | p=4 | S₄ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 256 | 25.866 | 40.679 | 36.084 | 37.581 | 0.69 |
| 65536 | 26.857 | 41.299 | 37.853 | 35.608 | 0.75 |

У цій серії S₄ < 1: OpenMP-версія повільніша за власну послідовну базу. Додаткові копії, алокації та керування паралельною областю не окупилися на рівні повного сортування; окремі фази не профілювалися.
